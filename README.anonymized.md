# [PRODUCT_1] — Резюме проекта

## Что это такое

**[PRODUCT_1]** — это локальный прокси-сервер на [PRODUCT_2], который сидит между клиентом ([ORG_3]) и облачными LLM ([ORG_4]). Его задача — анонимизировать запросы (NER + плейсхолдеры), отправлять их в облако, получать ответы и де-анонимизировать их обратно.

Помимо прозрачной автоматической анонимизации, прокси поддерживает **ручное
управление**: пользователь может (1) отправить промпт сразу без анонимизации,
(2) анонимизировать и просмотреть/отредактировать результат, (3) отправить
отредактированный анонимизированный промпт; при работе с файлами модель правит
анонимизированную копию, а де-анонимизация выполняется только в самом конце.

Это позволяет использовать облачные LLM (например, [PRODUCT_5]) без раскрытия
чувствительных данных (PII) третьим лицам.

## Архитектура

```
[[ORG_3]] → [[PRODUCT_1]] → [[ORG_4]]
                ↓
           [[PRODUCT_6]] (локальная NER)
                ↓
         [[ORG_7]] (для [ORG_4])
```

1. **[ORG_3]** отправляет запрос на `http://[PHONE_8]` (как будто это [ORG_4])
2. **Прокси** принимает запрос, анонимизирует его с помощью локальной NER-модели ([PRODUCT_6])
3. **Прокси** отправляет анонимизированный запрос в **[ORG_4]** через **[ORG_7]** (прокси на `[PHONE_9]`)
4. **[ORG_4]** возвращает ответ
5. **Прокси** де-анонимизирует ответ (заменяет плейсхолдеры на реальные значения)
6. **Прокси** возвращает ответ [ORG_3]

[PRODUCT_6] используется **только** для анонимизации (NER), не для генерации текста.

## Как это работает

### Режимы работы ([PRODUCT_32])

1. **`[POSITION_33]`** (по умолчанию) — полная обработка:
   - Запрос → анонимизация → [ORG_4] → де-анонимизация → ответ
   - Используется [PRODUCT_6] для NER и [ORG_4] для генерации
   - Канонический анонимизированный результат сохраняется в файл
     `[LOC_34]<session_id>/anonymized_request_*.[PRODUCT_19]`, путь —
     в `anonymization_metadata.anonymized_request_file` ответа
     (для стрима — в финальном control-чанке с `anonymization_metadata`,
     который идёт до `[DONE]`)

2. **`[POSITION_35]`** — только анонимизация, без облака (проверка конфиденциальности):
   - Запрос → анонимизация локальной моделью ([PRODUCT_6] NER) → сохранение
     результата в файл → ответ-заглушка. В облако ничего не отправляется,
     на этом обработка останавливается
   - Системные сообщения в анонимизации не участвуют и в результат не входят —
     сохраняется только полезная часть запроса
   - Анонимизированный запрос сохраняется в
     `[LOC_34]<session_id>/anonymized_request_*.[PRODUCT_19]`,
     путь к файлу возвращается в ответе
   - Позволяет посмотреть, в каком виде запрос ушёл бы в облако, и убедиться,
     что PII заменены плейсхолдерами

3. **`[POSITION_36]`** (основной для явной схемы) — запросы идут без анонимизации:
   - `/v1/chat/completions` не анонимизирует и не де-анонимизирует
     (прозрачный прокси); вся анонимизация — через явные вызовы `[PRODUCT_37]`
   - [ORG_3] работает в обычном режиме, инструменты плагина управляют
     анонимизацией шаг за шагом
   - **Исключение — авто-анонимизация приложенных файлов**: если в запросе
     есть команда анонимизации («анонимиз…» / «anonymis/z…» в user-сообщении)
     и блоки `<file_content path="...">` с файлами, прокси перехватывает
     запрос: анонимизирует файлы локальной NER-моделью (создаётся копия
     `<name>.anonymized.<ext>` + `.[PRODUCT_19]` для ревью, общая сессия маппингов)
     и возвращает клиенту список результатов **без обращения в облако**.
     Ответ содержит машиночитаемый маркер `[anonymizer:done:<путь>]` —
     по нему прокси не перехватывает повторно следующие запросы агента
     в том же диалоге (защита от зацикливания). Явное `anonymize: false`
     отключает и перехват тоже. Метаданные ответа:
     `anonymization_metadata.mode == "files_anonymization"`.

При любом `[PRODUCT_32]` запрос может передать `anonymize: false` —
принудительный [POSITION_36] для конкретного запроса.

### Канонический результат и маркеры выделения

Анонимизированный запрос имеет **единственное каноническое представление** —
markdown-рендер сообщений. Это гарантирует проверяемую цепочку
«то, что я вижу = то, что ушло в облако»:

- в **каждом режиме** канонический результат сохраняется в файл
  `[LOC_34]<session_id>/anonymized_request_*.[PRODUCT_19]`;
- в режиме `[POSITION_35]` ответ (стрим и не-стрим) содержит одну служебную
  строку техсведений (режим, session_id, путь к файлу, число сущностей и
  маппингов), а затем канонический результат между маркерами:

  ```
  [Режим: [POSITION_35]; session_id: ...; файл: ...; сущностей: N; маппингов: M]

  <<<ANONYMIZED_RESULT>>>
  ## user
  Проверь документ от [PERSON_1]
  <<<END_ANONYMIZED_RESULT>>>
  ```

  Результат извлекается программно regex
  `<<<ANONYMIZED_RESULT>>>\n(.*?)\n<<<END_ANONYMIZED_RESULT>>>` и **идентичен**
  содержимому файла. Техинформация дублируется в `anonymization_metadata`
  (`mode`, `session_id`, `anonymized_request_file`, `entities_found`,
  `mappings_count`; для стрима — в финальном чанке SSE);
- в режиме `[POSITION_33]` в облако уходят именно те `anonymized_messages`, из которых
  построен канонический результат: содержимое файла — проверяемая проекция
  фактически отправленного контекста.

**Архитектурная гарантия:** запрос к облачной модели конструирует только
прокси. Локальная модель в [PRODUCT_6] используется исключительно для NER —
она возвращает список сущностей (JSON) и не формирует никаких запросов
в облако.

### Процесс анонимизации

0. **Извлечение приложенных файлов** (оба режима):
   - Если клиент ([ORG_3]) приложил файл, но не смог его прочитать (типично для
     бинарных документов [PRODUCT_15]/[PRODUCT_16]), в тексте сообщения появляется блок
     `<file_content path="...">Error fetching content: ...</file_content>`
   - Прокси обнаруживает такие блоки, сам читает локальный файл по указанному
     пути (поддерживаются абсолютные пути, относительные от корня workspace
     и `file://` URI) и извлекает текст через `FileParser`
     ([PRODUCT_15]/[PRODUCT_16]/[PRODUCT_17]/[PRODUCT_18]/[PRODUCT_19])
   - Извлечённый текст подменяет заглушку-ошибку и дальше участвует в NER и
     анонимизации наравне с остальным текстом запроса
   - Если файл не найден или формат не поддерживается — блок остаётся без
     изменений, запрос не падает (в лог пишется предупреждение)
   - Извлечение через `FileParser` — **основной механизм** попадания содержимого
     офисных документов в анонимизацию: успешно прочитанные клиентом
     `<file_content>`-блоки не подменяются; маппинги общие для сессии, поэтому
     одна и та же PII получает один и тот же плейсхолдер
   - Для [PRODUCT_15] и [PRODUCT_16] `FileParser` сохраняет простейшую структуру: абзацы и
     таблицы Word, листы и ячейки Excel. Обратная сборка (`FileAssembler`,
     эндпоинт `[PRODUCT_38]`) записывает анонимизированный текст обратно
     по координатам сегментов: сетка таблиц сохраняется, а неизменённые
     ячейки (включая формулы, числа и даты Excel) не затрагиваются
1. **NER** (Named Entity Recognition):
   - Использует локальную модель в [PRODUCT_6] (`[PRODUCT_39]`)
   - Выявляет PII: имена, должности, организации, телефоны, email, ИНН, адреса, суммы
   - Поддержан **thinking-режим** модели: если итоговый ответ в `content` пуст,
     прокси ищет JSON с сущностями в `reasoning_content` (берётся последний
     JSON, промежуточные игнорируются)
   - Модель возвращает только текст и тип сущностей; **оффсеты в тексте
     вычисляет сам прокси** (точное совпадение + поиск без учёта регистра
     и различия ё/е) — ошибки модели в оффсетах больше не теряют сущности
   - Для оргформ с названием в кавычках (`[ORG_40]`) прокси дополнительно
     выделяет ядро (`[ORG_41]`) и заменяет также все короткие вхождения названия
     — разрозненные упоминания одной компании не утекают в облако
   - Поиск сущностей устойчив к написанию: регистр, ё/е и визуально одинаковые
     буквы кириллицы/латиницы (`«1С»`/`«1C»`) считаются совпадением —
     значение, возвращённое моделью в одном алфавите, покрывает вхождения
     в другом
   - Промпт требует помечать в том числе широко известные организации,
     госорганы, имена с инициалами и все варианты названия одной компании;
     итоговое качество детекции зависит от локальной модели
   - Текст длиннее `[PHONE_42]` (по умолчанию [MONEY_43] символов —
     лимит по VRAM) разбивается на чанки с перекрытием 500 символов;
     сущности переносятся в координаты исходного текста, поэтому границы
     чанков не теряются. Короткие тексты идут одним вызовом
   - Детерминированная страховка: оргформы (ООО/АО/ПАО/ОАО/ЗАО/НКО/НПФ/ГК,
     Фонд/Банк + название) ловятся regex с учётом регистра даже если LLM
     их пропустила
2. **Замена**:
   - PII заменяется плейсхолдерами вида `[Имя_1]`, `[Организация_1]`, `[Телефон_1]`
   - Если значение признано PII хотя бы один раз, заменяются **все** его
     точные вхождения в тексте (LLM часто пропускает повторные упоминания);
     одно и то же значение всегда получает один и тот же плейсхолдер
   - Маппинги сохраняются в SQLite (`[PRODUCT_44]`) с TTL 24 часа
3. **Отправка в облако**:
   - Анонимизированный запрос отправляется в [ORG_4]
   - Модель генерирует ответ (без знания реальных данных)
4. **Де-анонимизация**:
   - Ответ от [ORG_4] проходит обратную замену плейсхолдеров на реальные значения
   - Возвращается клиенту

### Хранение данных

## Требования к настройке [PRODUCT_6]

Локальная модель в [PRODUCT_6] выполняет NER (анонимизацию). Требования:

1. **Сервер**: [PRODUCT_6] запущен, локальный сервер включён на
   `[PHONE_51]` (по умолчанию `http://localhost:1234`, путь `/v1`),
   OpenAI-совместимый API отвечает на `[PHONE_80]` и
   `[PHONE_81]`.
2. **Модель**: для NER загружена модель, и значение `[PRODUCT_53]` в `[PRODUCT_29]`
   **точно совпадает** с её идентификатором в [PRODUCT_6] (см. список в
   `GET [PHONE_52]/models`). По умолчанию `[PRODUCT_39]`.
3. **Thinking-режим** (рассуждения модели): поддерживается прокси в обоих
   состояниях — и включён, и выключен.
   - При включённом thinking итоговый ответ приходит в `content`, а
     рассуждения — в `reasoning_content`; если `content` пуст, прокси
     разбирает `reasoning_content`.
   - **Reasoning budget** (настраивается в [PRODUCT_6] для модели): должен быть
     достаточным, чтобы модель успевала выдать итоговый JSON с сущностями.
     Если бюджет мал, ответ обрезается (`finish_reason=length`), JSON не
     появляется, и прокси пишет в лог предупреждение
     «[PRODUCT_6] не вернул JSON с сущностями…» — увеличьте Reasoning budget
     или `[PHONE_54]` в `[PRODUCT_29]`.
4. **Контекст**: окно контекста модели должно вмещать `[PHONE_42]`
   символов текста плюс запас на системный промпт и ответ
   (`[PHONE_54]`). Текст длиннее автоматически режется на чанки
   с перекрытием.
5. **Таймаут**: обработку больших документов локальной моделью ограничивает
   `[PHONE_56]` (по умолчанию [MONEY_57] с). Thinking-режим заметно
   увеличивает время ответа — закладывайте это в таймаут.

## Ручное управление анонимизацией

В явной схеме (`[PRODUCT_32]=[POSITION_36]`) анонимизация выполняется
отдельными шагами через эндпоинты `[PRODUCT_37]`:

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `[PRODUCT_38]` | Анонимизировать текст (без облака), вернуть `.[PRODUCT_19]` |
| POST | `[PRODUCT_72]` | Анонимизировать локальный файл: создать копию `<name>.anonymized.<ext>` + `.[PRODUCT_19]` для review |
| POST | `[PRODUCT_73]` | Отправить анонимизированный промпт в облако, вернуть де-анонимизированный ответ |
| POST | `[PRODUCT_75]` | Заменить плейсхолдеры в файле на реальные значения (финальный шаг) |
| GET | `[PRODUCT_76]` | Список активных сессий |
| POST | `/v1/chat/completions` с `anonymize: false` | Отправить промпт сразу в облако без анонимизации |

Файлы ([PRODUCT_15]/[PRODUCT_16]) извлекаются в **markdown с таблицами** — и для review, и для
отправки в облако. Модель редактирует анонимизированную копию файла, а
де-анонимизация выполняется в самом конце.

### Использование в интерфейсе

Есть два готовых интерфейса: **[ORG_3] SDK-плагин** (`[PRODUCT_23]`) и
**VS Code-расширение** (`[PRODUCT_22]`). Пользователь пишет промпт в [ORG_3]
и выбирает одно из действий.

**Через [ORG_3] (плагин с инструментами).** Установка: скопируйте папку
`[PRODUCT_23]` (без `node_modules`) в один из путей поиска плагинов [ORG_3] —
глобально `[LOC_106]` или в
`[LOC_107]` (подробности и
вариант через `[PHONE_108]` — в `[PRODUCT_23]README.[PRODUCT_19]`).
**Важно:** [ORG_3] сканирует плагины от корня открытого workspace и из
глобального каталога — сам каталог `[PRODUCT_23]` в репозитории не
подхватывается автоматически; после установки перезагрузите окно VS Code.
В чате [ORG_3] пользователь просит модель вызвать нужный инструмент:

1. **Анонимизировать текст** — «вызови `[PRODUCT_24]` с текстом …» → прокси
   анонимизирует и возвращает анонимизированный текст + `session_id` + путь `.[PRODUCT_19]`.
2. **Анонимизировать файл** — «вызови `[PRODUCT_25]` для `[LOC_109]\документ.[PRODUCT_15]`» →
   создаётся копия `<name>.anonymized.<ext>` с плейсхолдерами (структура и
   таблицы сохраняются) + форматированный `.[PRODUCT_19]` для ревью.
3. **Просмотр/редактирование** — открыть `.[PRODUCT_19]` (markdown с таблицами) и проверить,
   что PII заменены плейсхолдерами; при необходимости поправить.
4. **Отправить анонимизированный промпт** — «вызови `[PRODUCT_26]` с `session_id`
   и контентом» → прокси отправляет в облако и возвращает **де-анонимизированный**
   ответ.
5. **Если модель меняла файл** — модель правит анонимизированную копию
   (`<name>.anonymized.<ext>`), а в самом конце «вызови `[PRODUCT_27]`» →
   плейсхолдеры заменяются реальными значениями.
6. **Отправить сразу (без анонимизации)** — обычный запрос [ORG_3] с
   `anonymize: false` ([POSITION_36]) — промпт уходит в облако «как есть».

показывает список активных сессий (session_id, время, количество маппингов).
