## 1. Текущее состояние (что есть сейчас)

| Требование | Как сейчас |
|---|---|
| Выделяемый результат в ответе | В `anonymize_only` ответ — это прозаический текст «[Режим анонимизации] … НЕ отправлен в облако … файл сохранён …» + JSON-дамп `anonymized_messages` (`handlers.py:361-367`, `522-528`). Результат «утоплен» в тексте, программно не выделяется. Бонусная несогласованность: в **файл** пишется markdown-рендер (`_render_messages_markdown`), а в **ответ** — сырой JSON. Это два разных представления. |
| Сохранение в файл | Только в режиме `anonymize_only` (`_save_anonymized_request`). В режиме `full` анонимизированный запрос никуда не сохраняется (только JSON-лог в БД). |
| Кто конструирует запрос к облаку | Формально уже прокси: локальная модель в LM Studio возвращает только JSON с сущностями (`NER_SYSTEM_PROMPT`), список `anonymized_messages` собирает `RequestHandler._anonymize_messages`, и именно он уходит в OpenRouter. Однако нет гарантии, что «выделяемый результат» (то, что видит человек в файле/ответе) и то, что реально ушло в облако, — одно и то же представление. Сейчас они расходятся (markdown vs JSON). |

## 2. Соображения о целесообразности

**За:**
1. **Аудитируемость и доверие.** Главная ценность прокси — гарантия «в облако не ушло PII». Если единый канонический результат (а) легко выделяется из ответа, (б) всегда пишется в файл, (в) является частью контекста, отправляемого в облако, — появляется строгая проверяемая цепочка: «то, что я вижу = то, что ушло в облако». Сейчас в режиме `full` пользователь вообще не видит анонимизированный вид запроса вне БД-логов.
2. **Устранение расхождения представлений** (markdown в файле vs JSON в ответе) снимает целый класс ошибок при ручной проверке.
3. **Машиночитаемость.** Маркеры/метаданные позволят Cline или скриптам извлекать результат без парсинга русскоязычной прозы.
4. **Рефакторинг локален:** все три требования касаются по сути одного места — `handlers.py` + одна строка в тестах/README. Инфраструктура (`save_anonymized_text`, `anonymization_metadata`) уже существует.

**Против / риски:**
1. Сохранение файла в `full`-режиме увеличит объём данных на диске (хотя файлы не содержат PII — оригиналы не сохраняются).
2. Изменение формата ответа `anonymize_only` сломает существующие тесты (`test_anonymize_only.py` проверяет фразы «НЕ отправлен в облако») — тесты нужно будет обновить, а не обойти.
3. Пункт 3 двусмыслен: «запрос к облачной модели должен конструировать прокси» де-факто уже выполняется. Я трактую его как требование *гарантировать и зафиксировать* это архитектурно: канонический выделяемый результат = единственный источник контекста для облака. Если вы имели в виду другое (например, двухфазный сценарий: anonymize_only → человек проверяет файл → отдельный вызов отправляет содержимое файла в облако) — скажите, план скорректирую.

**Вывод: рефакторинг целесообразен и реализуем** без новых зависимостей, изменения локализованы в 2–3 файлах.

## 3. План рефакторинга

### Шаг 1. Каноническое представление результата (`proxy/handlers.py`)
- Сделать markdown-рендер (`_render_messages_markdown`) единственным представлением анонимизированного запроса: `PreparedRequest` получает поле `canonical_result: str` (markdown), вычисляемое один раз в `prepare_chat_request`.
- Ввести маркеры выделения, например константы в `config.py`:
  - `RESULT_BEGIN = "<<<ANONYMIZED_RESULT>>>"`, `RESULT_END = "<<<END_ANONYMIZED_RESULT>>>"`

### Шаг 2. Сохранение файла в обоих режимах
- В `handle_chat_completion` (ветка `full`, не-стрим) и в `stream_from_prepared` (ветка `full`) вызывать `_save_anonymized_request(session_id, ...)` — сейчас это делается только в ветках `anonymize_only`. Путь добавлять в `anonymization_metadata.anonymized_request_file`.
- Файл и ответ строятся из одного `canonical_result` — гарантируется идентичность.

### Шаг 3. Формат ответа в `anonymize_only` (стрим и не-стрим)
- `message.content` содержит только: одну служебную строку с минимумом техсведений (режим, session_id, путь к файлу, число сущностей) + результат между маркерами. Вся структурированная техинформация дублируется в `anonymization_metadata` (поле уже есть в схеме `ChatCompletionResponse`): `{"mode", "session_id", "anonymized_request_file", "entities_found", "mappings_count"}`.
- Убрать из контента JSON-дамп сообщений — вместо него markdown `canonical_result`.
- Для стрима (`_stream_anonymize_only`) — та же структура: техсводка, затем канонический результат чанками между маркерами; в финальном чанке можно добавить `anonymization_metadata`.

### Шаг 4. Запрос к облаку конструирует прокси, результат — часть контекста
- Архитектурно зафиксировать: в `full`-режиме в OpenRouter уходят `anonymized_messages`, из которых построен `canonical_result` (тот же объект-источник). В документации и коде явно указать: локальная модель используется **только** для NER (возвращает сущности), формирование любых запросов в облако — прерогатива прокси; `canonical_result` — проверяемая проекция фактически отправленного контекста.
- Опционально (по вашему решению): в `full`-режиме добавлять в отправляемый контекст служебное system-сообщение вроде «Контекст анонимизирован; плейсхолдеры вида `[PERSON_1]` — заменённые PII» — но это уже поведенческое изменение, по умолчанию не делаю.

### Шаг 5. Тесты
- Обновить `tests/test_anonymize_only.py`: проверка наличия маркеров, канонического markdown вместо JSON, отсутствия прозаической обёртки внутри маркеров.
- Добавить тест: в `full`-режиме (не-стрим и стрим) вызывается `save_anonymized_text` и путь присутствует в метаданных; содержимое файла совпадает с результатом между маркерами.
- Прогнать все три тестовых файла: `test_fixes.py`, `test_anonymize_only.py`, `test_tools_passthrough.py`.

### Шаг 6. Документация
- Обновить `README.md`: новый формат ответа `anonymize_only` с маркерами, сохранение файла в обоих режимах, явная фиксация того, что облачный запрос конструирует прокси.

### Критерии приёмки
1. Ответ `anonymize_only`: результат извлекается regex `<<<ANONYMIZED_RESULT>>>(.*?)<<<END_ANONYMIZED_RESULT>>>` в стриме и не-стриме.
2. После вызова в любом режиме существует файл `data/anonymized_files/<session_id>/anonymized_request_*.md`, и его содержимое идентично выделенному результату.
3. В облако уходит контекст, чья проекция = содержимое файла.
