# Code Review: Anonymizer Proxy

Дата: 2026-08-06
Обзор: все модули пакета `anonymizer_proxy/` + README, .env, requirements.

## Общая оценка

Проект хорошо структурирован: чистое разделение на слои (`anonymizer/`, `proxy/`, `models/`), внятные Pydantic-схемы, поддержка стриминга (SSE), подробный README. Архитектура «regex + LLM» для NER — разумная. Однако есть **критические проблемы безопасности** и **серьёзная функциональная ошибка** в ядре анонимизации.

---

## 🔴 Критично (безопасность)

### 1. Сервер без аутентификации доступен из сети, через него можно получить ВСЕ PII
`PROXY_HOST=0.0.0.0` (`config.py`) + полное отсутствие авторизации. Любой в сети может:
- `GET /api/logs` — возвращает `original_content` (исходные PII в plaintext);
- `POST /api/deanonymize` — восстанавливает реальные значения по session_id;
- `GET /api/logs/export` — выгружает PII в файл.

Это перечёркивает цель проекта: PII не уходят в облако, но доступны любому по HTTP.
**Исправление:** bind на `127.0.0.1` по умолчанию + токен для `/api/*` эндпоинтов.

### 2. Реальный API-ключ в `.env` без `.gitignore`
`.env` содержит реальный `OPENROUTER_API_KEY`. В проекте нет `.gitignore` — файл попадёт в git.
**Исправление:** отозвать/пересоздать ключ, добавить `.gitignore` (`.env`, `data/`, `*.log`, `*.db`).

### 3. CORS: `allow_origins=["*"]` + `allow_credentials=True`
`main.py`: недопустимая комбинация для сервиса с чувствительными данными.
**Исправление:** убрать CORS или ограничить конкретными origin.

### 4. Path traversal в `/api/logs/export`
`session_id` из query-параметра без валидации попадает в имя файла — значение вида `../../evil` запишет файл за пределы `LOGS_DIR`.
**Исправление:** валидация формата session_id (UUID/`[A-Za-z0-9_-]`).

## 🟠 Серьёзная функциональная ошибка

### 5. Позиции сущностей неверны при анонимизации нескольких сообщений
В `handlers.py`:
1. Тексты всех сообщений склеиваются: `combined_text = "\n".join(all_text)`;
2. NER возвращает `start/end` относительно склеенного текста;
3. Затем каждое сообщение анонимизируется по отдельности теми же сущностями;
4. `TextReplacer.anonymize` режет текст по абсолютным позициям.

Для диалога из >1 сообщения оффсеты из второго/третьего сообщения превышают длину сообщения — Python-слайсы не падают, а молча портят текст. Корректно работает только для одномесседжных запросов.
**Исправление:** анонимизировать склеенный текст и разбить обратно, либо пересчитать оффсеты на каждое сообщение, либо искать `entity.text` в пределах сообщения.

### 6. Позиции от LLM не валидируются
`ner_service.py`: `start/end` из ответа LM Studio принимаются на веру. LLM регулярно ошибается в оффсетах — любая ошибка повреждает текст при замене.
**Исправление:** сверять `text[start:end] == ent["text"]`, при несовпадении — `text.find()` или отбрасывать.

### 7. Токены разрезаются при стриминге
Де-анонимизация выполняется на каждом чанке отдельно. Токен `[PERSON_1]` придёт разорванным (`"[PER"` + `"SON_1]"`) — замена не сработает, плейсхолдер утечёт к клиенту.
**Исправление:** буферизовать хвост чанка с потенциальным токеном.

## 🟡 Средние проблемы

8. `replacer.deanonymize` использует `re.sub` с небезопасной заменой: `original_value` интерпретируется как шаблон (обратные ссылки `\1`, `\g<...>` ломают замену). Достаточно `str.replace` или единого regex с callback.
9. Каскадная де-анонимизация: если `original_value` содержит `[PERSON_2]`, последовательные замены дадут непредсказуемый результат. Нужен один проход.
10. Print-логирование повсеместно вместо модуля `logging`: нет уровней, ротации, возможности отключить.
11. Дублирование кода: `handle_chat_completion_stream` — мёртвый код (`main.py` использует `prepare_chat_request` + `stream_from_prepared`); та же логика задублирована между `prepare_chat_request` и `handle_chat_completion`. ~200 строк можно удалить.
12. SQLite: новое соединение на каждую операцию, нет WAL-режима — под нагрузкой возможны `database is locked`.
13. Рассинхронизация TZ: в БД `CURRENT_TIMESTAMP` (UTC), в коде `datetime.now()` (локальное).
14. `/api/deanonymize` принимает текст через query-параметры — длинные тексты упрутся в лимит URL. Нужна модель тела запроса.
15. Статус апстрима извлекается regex из строки исключения — нужен собственный класс исключения с `status_code`.
16. Сборка DOCX/XLSX/XML рассинхронизируется, если значения содержат переводы строк (`split("\n")`).
17. Голый `except:` в `openrouter_client.py` — подавляет все ошибки.

## 🟢 Мелкие замечания

- Поле `anonymize: bool` в `ChatCompletionRequest` объявлено, но нигде не проверяется.
- Неиспользуемый импорт `sqlite3` в `mapping_store.py`; `python-multipart` в зависимостях не используется.
- Несовпадение порта: дефолт в `config.py` — 8080, README и `.env` — 8081.
- `HTTP-Referer: http://localhost:8080` захардкожен.
- `sys.path.insert` хак в `main.py` — лучше `pip install -e .` с `pyproject.toml`.
- `check_lm_studio()` делает HTTP-вызов на каждый запрос — нужен короткий кэш.
- `Генеральному директору ООО.docx` и `data/anonymizer.db` (с PII) не должны попадать в VCS.
- Нет тестов в пакете, нет CI/Dockerfile.
- Regex для INN (`\d{10,12}`) даёт ложные срабатывания на любых длинных числах.

---

## Что хорошо

- Отличный README — объясняет и архитектуру, и грабли.
- Чистая слоистая архитектура и DI через конструктор `RequestHandler`.
- Грамотная идея: NER+анонимизация ДО `StreamingResponse`, чтобы ошибки возвращались нормальным JSON.
- Корректные SSE-заголовки (`X-Accel-Buffering: no`), поддержка мультимодального контента.
- TTL маппингов и cleanup-эндпоинт.

## Рекомендуемый приоритет исправлений

1. Bind на 127.0.0.1 + аутентификация (или firewall).
2. Отозвать API-ключ из `.env`, добавить `.gitignore`.
3. Исправить оффсеты сущностей при мультисообщениях.
4. Буферизация токенов в стриминге.
5. Валидация LLM-оффсетов + безопасная замена.
6. Убрать мёртвый код, перейти на `logging`.
